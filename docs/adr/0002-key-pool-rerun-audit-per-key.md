# 0002 — 多組 API Key 輪替：換 Key 時整次稽查重跑，PUUID 依 Key 分開存

## 狀態
已採納（2026-11-21）

## 背景
使用者要能存放多組 Personal API Key，當前一組進入冷卻時自動換下一組。但 Riot 的 PUUID 依 Key 持有者加密，不同 Personal Key 查同一位玩家會得到不同的 PUUID。可能多排、相遇、本人、黑名單都以 PUUID 跨對戰比對，混用兩組 Key 抓到的資料不會報錯，而是**安靜地判斷錯誤**（例如多排標不出來、黑名單不標紅）。

## 決定
- 一次稽查（含「查對面」）的所有資料都必須出自同一組 Key。查到一半換 Key 時，**整次稽查用新 Key 從頭重跑**，不沿用舊 Key 已查到的任何結果。
- 本人的 PUUID 與黑名單的每一筆，**每組 Key 各存一份**。新增 Key 時，用既有的 Key 把黑名單的每筆 PUUID 查回對方目前的 Riot ID，再用新 Key 換成新版 PUUID；刪除 Key 時一併刪掉該版本。

## 考慮過的選項
- **只重查還沒查完的玩家**，並記錄每筆資料出自哪組 Key、比對時再換算：省請求，但分析邏輯要全面改寫，往後每個跨玩家的功能都得處理多種 PUUID 版本。沒有採用。
- **新增 Key 時檢查 PUUID 是否與現有 Key 一致、不一致就拒絕**：簡單，但不同 Personal Key 幾乎一定加密不同，等於多組 Key 加不進去。沒有採用。

## 取捨
- 換 Key 時，舊 Key 已用掉的請求（一次稽查約 35–40 次）會白費。
- Riot 開發者政策禁止用多組 Key 繞過限速；這是個人工具，使用者知情並自行承擔風險。
- 實作（#11）：本地限速要等不到 2 秒（每秒 20 次的視窗，幾乎每次稽查都會碰到）不算冷卻、不換 Key，免得為了等不到 1 秒白費整次稽查的請求。
- 實作（#11）：同一次稽查因冷卻換 Key 最多換「Key 數」次，之後留下來等；否則一次稽查的請求數超過單組 Key 的 2 分鐘額度時，會在幾組 Key 之間永遠重跑。
- 後續（#12，2026-11-21）：黑名單整個移除。它要靠一組還能用的舊 Key 把每筆換算成新 Key 的版本，唯一的 Key 失效後重新產生時無從換算，紅卡會安靜地消失；使用者平常也很少用。現在依 Key 分開存的只剩本人的 PUUID。
- 後續（#25，2026-11-21）：黑名單加回來，但不再用舊 Key 換算。每筆同時記 Riot ID 與各組 Key 的 PUUID：
  - 這組 Key 有版本時以 PUUID 比對。
  - 沒有版本時以 Riot ID 比對，比對到就記下這組 Key 的 PUUID。
  - 稽查本來就會查到每個人的 Riot ID 與 PUUID，所以不需要額外請求，也不依賴舊 Key 還能用。
  - 刪除 Key 只刪該版本，整筆保留。
  - 代價：對方改名、而且換 Key 後還沒遇過他時認不出來。
